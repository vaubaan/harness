# Optional pillar `docs/quality/` for project quality rules

> **Amended (2026-10-22)** by
> [no-personas-no-code-judgment](./no-personas-no-code-judgment.md):
> `clean-code-guardian` is removed from the harness. The pillar, its
> linter and its mention in `AGENTS.md` stand; agents read the file
> directly. The number of linters is no longer 14.

## Context

The `clean-code-guardian` skill carries **generic** quality criteria,
identical for every project. Before auditing, it reads `AGENTS.md`,
`docs/spec/` and `docs/handbook/`, but none of these locations is meant
to state a project's own quality rules: naming conventions, chosen
patterns, thresholds, and above all deliberate deviations from the
generic criteria.

Observed consequences:

- `AGENTS.md` is regenerated by the harness: it cannot carry project
  content.
- Rules end up scattered across handbooks, which describe the state of
  the code, not a norm.
- The audit cannot tell a defect from an accepted convention, which
  produces recurring false positives.
- Nothing tells the audit which checks are already performed by
  automated tools (formatting, static analysis, typing).

v2 had a `quality.md`, which disappeared without a decision during the
move to six pillars ([spec §17.5](../spec/coding-agent-harness.md)). The
spec excluded any additional pillar in v1; that lock has already been
lifted once for
[`docs/skills/`](./project-skills-seventh-pillar.md).

## Decision

Introduce `docs/quality/` as an **optional pillar**, with a single
required file: `docs/quality/code-quality.md`.

The file is normative and has three required sections:

1. **Mechanical checks** — the project's tools, their configuration
   file and their scope. Pointers only: the configuration remains the
   source of truth.
2. **Project rules** — the judgment rules that no tool checks.
3. **Accepted deviations** — the generic rules not followed, each with
   its reason.

French section names remain accepted by the linter for backward
compatibility.

Integration into the harness:

- New linter `lint:quality-schema`: if `docs/quality/` exists, the
  required file and its three sections are mandatory; if the directory
  is absent, the linter reports nothing.
- `docs/quality` is not among the required directories of
  `lint:doc-layout`.
- `clean-code-guardian` reads the file first when it exists, does not
  re-flag what the tools cover, and does not report an accepted
  deviation as a defect.
- `doc-audit` checks the pillar's shape and its boundaries.
- The `AGENTS.md` umbrella mentions the file in the "Project map" when
  it is present.
- A `code-quality.md.tmpl` template is shipped. No dedicated writer
  skill or command.
- No `tracks:`: the file sets a norm, it does not follow the code.

## Consequences

- A project has a versioned, reviewed location for its quality rules;
  the code audit has an explicit reference.
- No impact on existing projects: without `docs/quality/`, rendering,
  lint and audit are unchanged.
- The number of linters goes from 13 to 14.
- Risk of overlap with ADRs, the handbook and the tool configuration.
  It is bounded by the boundaries written in
  [spec §9.1.2](../spec/coding-agent-harness.md) and checked by
  `doc-audit`, not by a linter: detecting a paraphrase requires
  judgment (see [mechanical linters vs skills](./linters-mechanical-vs-skills.md)).
- The file can go stale if a tool is replaced: without `tracks:`, only
  review catches it. Accepted in v1.
- Possible future work: a dedicated writer skill if manual editing
  proves insufficient.

## Rejected alternatives

| Alternative | Reason for rejection |
|---|---|
| Put the rules in `AGENTS.md` | File regenerated by the harness and gitignored in the consumer; project content would be overwritten. |
| A handbook `docs/handbook/code-quality.md` | The handbook describes the *current how* and requires `tracks:`; a norm does not belong there and would blur the pillar boundary. |
| One ADR per rule | Suited to the *why* of a structural decision, not to a list of rules consulted at every audit. ADRs remain linked from the file. |
| Mandatory pillar | Would break the lint of every harnessed project and force an empty file where the generic criteria suffice. |
| Copy the tool configuration into the file | Double source of truth, guaranteed drift; we point to the configuration instead. |
| A project skill in `docs/skills/` that overrides `clean-code-guardian` | Requires duplicating the whole skill to change a few rules, and makes the project diverge from harness updates. |
| Ship a writer skill right away | Cost without proven use; the template and manual editing are enough to start. |
