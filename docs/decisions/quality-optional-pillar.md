# Optional pillar `docs/quality/` for project quality rules

## Context

A project's own code rules, naming conventions, chosen patterns,
thresholds and deliberate deviations from generic practice, had no
home. `AGENTS.md` is regenerated by the harness and cannot carry
project content; handbooks describe the state of the code, not a norm;
and nothing told an agent which checks the project's own tools already
perform.

The spec excluded any additional pillar in v1; that lock had already
been lifted once for [`docs/skills/`](./project-skills-seventh-pillar.md).

## Decision

`docs/quality/` is an **optional pillar** with a single required file,
`docs/quality/code-quality.md`. The file is normative and has three
required sections:

1. **Mechanical checks**: the project's tools, their configuration file
   and their scope. Pointers only; the configuration stays the source
   of truth.
2. **Project rules**: the judgment rules no tool checks.
3. **Accepted deviations**: the generic rules not followed, each with
   its reason.

French section names remain accepted by the linter.

Integration: `lint:quality-schema` requires the file and its sections
when `docs/quality/` exists and reports nothing otherwise;
`docs/quality` is not a required directory; `doc-audit` checks the
pillar's shape and boundaries; `AGENTS.md` lists the file in its
project map when present and tells agents to read it before writing or
auditing code; a `code-quality.md.tmpl` template is shipped. No
`tracks:`: the file sets a norm, it does not follow the code.

## Consequences

- A project has a versioned, reviewed location for its quality rules,
  read directly by agents.
- No impact on projects without `docs/quality/`.
- Overlap with ADRs, the handbook and tool configuration is bounded by
  the boundaries in [spec §9.1.2](../spec/coding-agent-harness.md) and
  checked by `doc-audit`, since detecting a paraphrase requires
  judgment ([linters-mechanical-vs-skills](./linters-mechanical-vs-skills.md)).
- Without `tracks:`, a replaced tool is only caught on review or by
  `doc-audit`.

## Rejected alternatives

| Alternative | Reason for rejection |
|---|---|
| Put the rules in `AGENTS.md` | Regenerated by the harness; project content would be overwritten. |
| A handbook `docs/handbook/code-quality.md` | The handbook describes the current *how* and requires `tracks:`; a norm does not belong there. |
| One ADR per rule | Suited to the *why* of a structural decision, not to a list consulted at every audit. |
| Mandatory pillar | Would break the lint of every harnessed project and force an empty file. |
| Copy the tool configuration into the file | Double source of truth, guaranteed drift. |
| A dedicated writer skill | Cost without proven use; the template and manual editing are enough. |
